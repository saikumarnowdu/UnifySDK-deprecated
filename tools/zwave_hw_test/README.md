# Z-Wave hardware test harness (Python + ctypes)

Automate **real-hardware** Z-Wave tests by binding the **zwapi** Serial API layer
directly in Python. This bypasses UCL, MQTT, and the full ZPC application so you
can validate NCP bring-up, transport, and command flows while iterating on C
changes with a smaller rebuild surface.

## What this tests

| Layer | Covered | Not covered |
|-------|---------|-------------|
| Serial API / zwapi | Yes | — |
| zwave_tx / attribute resolver | No | Use ZPC repo + Contiki loop |
| UCL / MQTT | No | By design |

## Quick start

```bash
# 1. Extract zwapi vendor tree from Unify v1.6.0 history (first time)
tools/zwave_hw_test/scripts/extract_zwapi_vendor.sh

# 2. Build shared library (~seconds, not full Unify)
tools/zwave_hw_test/scripts/build.sh

# 3. Run baseline requirements against your NCP
python3 tools/zwave_hw_test/run_hw_tests.py --port /dev/ttyUSB0
```

Set `ZWAVE_PYTHON_HARNESS_LIB` if the `.so` is not in `tools/zwave_hw_test/build/`.

## Python API

```python
from zwave_hw_test import ZwaveHarness, TransmitOptions

with ZwaveHarness("/dev/ttyUSB0") as z:
    print(z.get_protocol_version_string())
    z.send_nop(2, TransmitOptions.ACK)
    z.poll_until_tx_complete()
    print(z.get_last_tx_status())
```

## Requirement specs

YAML files under `python/zwave_hw_test/requirements/` drive `run_hw_tests.py`.
Edit `serial_baseline.yaml` or add new specs for your acceptance criteria
(NOP latency, Version CC reads, inclusion steps via raw `send_frame`, etc.).

Example step types: `get_version`, `send_nop`, `send_data`, `send_frame`,
`library_type`, `poll`.

## Rebuild scope

| Change | Rebuild command |
|--------|-----------------|
| Harness only | `cmake --build tools/zwave_hw_test/build --target zwave_python_harness` |
| zwapi vendor sources | same (static `zwave_hw_zwapi` relinks) |
| Full Unify / UCL | not required for this workflow |

## Vendor source

`vendor/` is generated by `extract_zwapi_vendor.sh` from git tag `ver_1.6.0`
(`fb360ad38^`). Optionally applies the zwapi portion of
`tools/zpc_serial_api_perf/0001-zwave-zwapi-serial-api-performance.patch`.

To use a live ZPC tree instead, point `ZWAPI_VENDOR_GIT_REF` or replace
`vendor/zwave_api` with your checkout.

## Extending to zwave_tx

For `zwave_tx` / `zwave_api_transport` testing without UCL:

1. Build those objects from the ZPC repository.
2. Add a second harness shared library that links them + a minimal Contiki stub.
3. Expose `zwave_tx_enqueue` / poll hooks via the same ctypes pattern.

This kit intentionally starts at **Tier 1–2** (Serial API + SendData/NOP) as the
fastest path to real-radio automation.
